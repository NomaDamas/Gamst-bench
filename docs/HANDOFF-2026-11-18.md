## 0. 벤치마크 전체 계획 (의도와 근거)

**무엇을 증명하려는가.** GAMST의 주장은 "항상 켜진 싼 지각(perception) + 시간적 메모리 + CallPolicy가 비싼 VLM을 *필요한 순간에만* 부르면, 매 프레임/주기적으로 VLM을 부르는 방식과 비슷하거나 나은 정답률을 훨씬 적은 VLM 호출·토큰으로 낸다"이다. 그래서 같은 입력·같은 백본·같은 채점기에서 **호출 정책만 바꾼 arm**을 비교한다.

| arm | 의미 | 이번 구현 |
| --- | --- | --- |
| A | VLM 중심(벤치 원래 방식) | 각 벤치 공식 native runner + 같은 백본 |
| C | GAMST 선택 호출 | `gamst_bench.extensions.*` + CallPolicy `sentinel` (변화 감지·질문·주기 감사) |
| D | 고정 주기 호출 | C와 동일 코드, CallPolicy `periodic` 5s → "선택"의 효과만 분리하는 ablation |
| A/C-gemini | 상용 백본 | Vertex Gemini 3 Flash로 A, C 반복 (사용자 승인된 BYOK/Vertex lane) |
| B, E | 경량 인식만 / 소형 상시 VLM | 이번 캠페인 미실행(GPU 1장). 다음 캠페인 과제 |

**벤치별 역할.** FastBench = 짧은 순간 사건·마감 시간 응답(transient). OmniPro = 오디오·영상 proactive alert·counting(오디오 의미는 Qwen3-VL이 못 받으므로 MiniCPM-o native만 오디오 사용, GAMST arm은 RMS만). StreamArena = 장시간 실시간 스트림의 현재·과거·proactive 질문(memory/retention). Inf-Streams(VSAS fallback)는 이번엔 미실행.

**보고 규칙.** (1) native A는 "NATIVE PROTOCOL · DEV SUBSET", C/D는 "GAMST EXTENSION · DEV SUBSET"로 분리 표기, 공식 리더보드 점수라고 하지 않는다. (2) 점수와 함께 backbone 호출 수·프롬프트 토큰·이미지 수·HTTP 오류(400/429)를 같이 보고한다 — GAMST의 이점은 비용 축에서 주장된다. (3) 실패·중단 arm도 지우지 않고 보고한다. (4) dev subset이라 통계적 결론(우위) 주장 금지; "dev-subset 관찰"로 쓴다. (5) 원본 산출물은 VM `/srv/gamst-runs/` → 로컬 `runs/gcp-2026-11-18/`(gitignore) 보관, 요약 JSON만 `data/campaigns/gcp-2026-11-18.json`으로 공개.

**표본.** FastBench: 300 record 중 seed 2026 무작위 50개(51 QA). OmniPro: 9 task × native 순서 앞 5개(45). StreamArena: 영상 `jFggESijmV4` 1개, RTP/HR/Pro 10문항. 전체 split은 GPU 1장·시간 제약으로 다음 캠페인.
